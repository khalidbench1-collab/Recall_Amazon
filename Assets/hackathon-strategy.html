one realistic bet.

A side-by-side read of the RevenueCat Shipaton and the Amazon Developer Hackathon — what the rules actually gate on, where the competition is thin, and five projects worth building.

Prepared 4 Sep 2026

Verdict: enter Amazon. Treat the Shipaton as optional.

Amazon gives you 22 more days, roughly 18× fewer competitors per prize dollar, and — decisively — no app-store gate. The deliverable is a GitHub repo and a 3-minute video, which is the format that plays to your strengths. The Shipaton's real obstacle was never writing the app; it was Google Play's mandatory 12-tester × 14-day window colliding with a 27-day deadline.

Rules that actually decide the outcome

RevenueCat Shipaton

!

Google Play's closed-testing requirement is the deadline killer

New personal developer accounts must run closed testing with 12 opted-in testers for 14 continuous days before production release. With 27 days left, registration has to happen immediately. An organization account skips this but needs a D-U-N-S number, which itself takes days.

!

The app must be brand new

First public release strictly between 1 Aug and 30 Sep 2026. Updates to anything previously shipped are disqualified outright.

1

RevenueCat SDK must power a real purchase

At least one in-app or web purchase, or ads served through RevenueCat Ads. This is genuinely about an hour of work with react-native-purchases.

2

Judges must be able to reach the paid tier

Ship either a free trial or a promo code. Forgetting this invalidates an otherwise complete entry.

3

Exact asset specs

Demo video ≤ 2 minutes on public YouTube/Vimeo, 1024×1024 icon, and at least one screenshot at 1179 × 2556 with no device frame. No third-party trademarks or licensed music.

4

Check the country exclusions first

Specific territories are barred. Verify eligibility in the official rules before spending a single dollar on a developer account.

Amazon Developer Hackathon

1

The repo must actually call the technology

For Alexa+, Bee and Ring, judges look for a real import, entry point, or loaded MCP config in the source — not a README mention. Fire TV is the sole exception: any framework passes, provided the video shows it running on a device or simulator.

2

Public repo, open-source licence, visible in About

The licence must be surfaced at the top of the repo, not buried in a file. This same requirement also satisfies most of the Open Source mini challenge.

3

Alexa+ has a guaranteed escape hatch

Self-hosted MCP server (spec 2025-11-25+, Streamable HTTP) or an Agent Skill — or a simulated Alexa+ experience as a web app, with no required framework. You cannot be hard-blocked on this track.

!

Bee requires hardware you don't have

The demo must use live data from a Bee device or an Apple Watch running Bee software. Skip this track.

4

Product feedback is mandatory, not decorative

Every tool, API and SDK you touched: what you used it for, what worked, what didn't, how onboarding felt, whether you'd use it again. Amazon is running this hackathon to harvest exactly this.

5

Friction logs carry up to a 10% judging bonus

Task attempted, steps taken, expected vs. actual, severity, workaround, actionable suggestion. Optional — which means most entrants will skip it. This is the cheapest 10% in either competition.

6

One project can win one track + one mini challenge

Not two tracks. So build one thing well and layer both mini challenges onto it.

The smart strategy

The governing insight is that these two events are won on completely different axes. The Shipaton's headline categories reward traction and revenue — outcomes you cannot manufacture in four weeks from a standing start against 23,000 people. Amazon rewards a working integration and a thoughtful write-up, both of which are fully within your control and finishable on a known schedule.

So: stop optimising for the biggest number on the page. Optimise for the prize whose judging criterion is a checklist you can complete.

Target the Alexa+ track

It carries the joint-highest prize in the Amazon event ($25k / $15k / $4k), needs zero hardware, and rests on MCP — a spec you already work inside daily. The simulated-web-app fallback removes tail risk entirely.

Stack both mini challenges onto the same project

One well-built MCP server is therefore eligible for $35,000 in cash plus $25,000 in AWS credits. The two mini challenges together represent perhaps a day of additional work.

Write the friction log as you build

Keep a running file open from day one. Every time something surprises you — bad error message, missing doc, confusing auth flow — log it on the spot with severity and a concrete suggestion. Reconstructing this at the end produces something obviously thin; capturing it live produces the single most differentiated part of your submission.

On the Shipaton: it stays viable only if you register a Play developer account this week, so the 14-day tester clock runs in the background while you build for Amazon. If that registration slips past roughly 10 September, drop it and commit fully to Amazon. Do not build two apps.

Sequence

  1. Day 0 — todayRegister for the Amazon hackathon; create the public repo with an MIT licence visible in AboutThe licence requirement is trivial now and easy to forget later. Registering locks in access to the SDKs and office hours.
  2. Days 1–3Set up the Alexa+ dev environment and get a hello-world MCP server responding over Streamable HTTPProve the riskiest technical link first. If self-hosting fights you, you learn it now — while the simulated-web-app fallback is still cheap to pivot to.
  3. Days 4–20Build the real tool surface, wired to BedrockBedrock instead of a direct API call is what converts this into an AWS Builder entry at essentially no cost.
  4. Days 21–30Harden, write the README so a judge can run it in five minutes, submit one PR to a public repoJudges who can't run your project fall back on the video alone. A runnable repo is a real scoring advantage.
  5. Days 31–42Record the demo video; lead with the strongest 30 secondsJudges aren't required to watch past three minutes. Front-load the payoff, explain the architecture second.
  6. Days 43–49Write the product feedback and friction log; submit with bufferNever submit on deadline day. Devpost submission forms have more required fields than anyone expects.

Five proposals

All five target Alexa+ and stack both mini challenges. Each is scoped to be genuinely buildable in 49 days, and each is chosen so the demo is convincing on video — the format the judging actually runs on.

1 · Recall

Alexa+ MCP · voice spaced repetition Top pick

A spaced-repetition study system exposed as MCP tools, so Alexa+ quizzes you out loud while you cook, drive, or fold laundry — and grades your spoken answer for meaning, not exact wording.

Tool surface
  • list_due_cards
  • grade_response — semantic, via Bedrock
  • add_card from spoken input
  • get_streak_summary
Why it wins

Voice is genuinely the correct modality for recall drills — free recall beats visual recognition, which is a real cognitive-science result. That makes the demo persuasive rather than gimmicky, which is the difference between a project that looks like a tech demo and one that looks like a product. Hits the "education" priority use case.

Build risk

Low SQLite + the SM-2 algorithm (well-documented, ~60 lines). No third-party APIs, no auth, no hardware.

Demo shape

"Alexa, quiz me on my biology deck." Answer aloud, slightly wrong. It catches the nuance, explains, reschedules the card. That's the whole 90 seconds.

2 · Handoff

Alexa+ MCP · household operations

Shared household state — lists, chores, who's collecting whom — as an MCP server, so any family member can query or update it by voice without opening an app or negotiating over a group chat.

Tool surface
  • get_open_items filtered by person
  • claim_task / complete_task
  • add_to_list with dedupe
  • whos_doing_what — daily rollup
Why it wins

Sits squarely in the "personal productivity" priority, and the multi-user angle shows off something a single-user app can't: shared state resolved through natural language. Unglamorous, but judges reward integrations that look like they'd survive contact with a real household.

Build risk

Low CRUD over a small store. The only real design work is conflict handling when two people claim the same task.

Demo shape

Two voices, one kitchen. One adds a task, the other claims it, the rollup reflects both. Simple and immediately legible.

3 · Plainspoken

Alexa+ MCP · accessibility Strong differentiator

A voice-first bridge that answers questions about a home's state in plain language for low-vision and blind users — turning dashboards, notifications, and status screens into things you can simply ask about.

Tool surface
  • describe_home_state — narrative, not tabular
  • whats_changed_since
  • explain_notification
  • set_priority_alerts
Why it wins

Accessibility is a named priority category, and it's the one where a thoughtful entrant stands out most sharply — the field is usually thin and the submissions that do appear are often superficial. Crucially, this is one of the few ideas where voice isn't a novelty layer; it's the entire access mechanism.

Build risk

Medium The engineering is easy; the language design is the hard part. Getting descriptions genuinely useful rather than verbose takes iteration.

Demo shape

Screen off, entirely audio. Ask what's happening; get a compact, well-ordered spoken answer. The absence of visuals is the demo.

$35,000Alexa+ 1st + Open Source + AWS Builder
One caveat: validate with at least one actual low-vision user before submitting. Judges in accessibility categories can reliably tell well-meaning guesswork from the real thing, and it counts against you.

4 · Standup

Alexa+ MCP · developer experience

Ask your repo what happened. An MCP server over git history, CI status, and open PRs that answers "what broke overnight?" or "what did I leave half-finished on Friday?" conversationally.

Tool surface
  • whats_red — failing CI, summarised
  • my_open_work across branches
  • summarize_changes_since
  • whos_blocked_on_me
Why it wins

"Developer experience" is an explicitly named priority, and Amazon's judges are developers — they feel this pain personally. Reading a CI dashboard is genuinely worse than asking a question, so the value proposition needs no explanation.

Build risk

Low GitHub's REST API is excellent and well-documented. The work is summarisation quality, not plumbing.

Demo shape

Monday morning, coffee in hand, no laptop open yet: "What broke over the weekend?" One spoken paragraph replaces ten minutes of dashboard archaeology.

5 · Rehearse

Alexa+ MCP · conversational practice

Practise difficult conversations out loud before they're real — giving critical feedback, declining a request, setting a boundary — with an AI counterpart that pushes back realistically, then scores you on clarity, empathy and firmness.

Tool surface
  • start_scenario from a library
  • respond_in_role — the counterpart
  • score_exchange on three axes
  • review_session with transcript
Why it wins

Voice-native by nature — you cannot rehearse a spoken conversation by typing. The scenario library is the product, so quality scales with writing effort rather than engineering effort, which is the right trade for a 49-day window. Doubles as a RevenueCat Shipaton entry if you pursue both.

Build risk

Medium Multi-turn roleplay state is fiddlier than the others here, and inference cost per session is real — budget the Bedrock credits.

Demo shape

Rehearse turning down extra work. The counterpart pushes back twice. Then the scorecard, with one specific line quoted back and improved.

$35,000Alexa+ 1st + Open Source + AWS Builder

If you build one thing

Build Recall. It has the lowest technical risk of the five, no external API dependency, a demo that lands inside 90 seconds, and it sits on a named priority use case. The spaced-repetition algorithm is public and small, which means nearly all your remaining time goes into polish and the write-up — and in a competition judged on the build plus the feedback, polish and the write-up are the score.

Plainspoken is the higher-variance alternative: a thinner field and a stronger story, at the cost of needing real user validation to be credible.
