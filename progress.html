Stages

  1. Foundation

    Day 0 · 4 SepDone

    Repo, licence and the written record, before any code. The licence requirement is trivial now and easy to forget later.

    • Git repository initialised on main
    • MIT licence at repo root
    • README with the pitch and run instructions
    • Architecture and design spec written
    • Friction log and product feedback files opened
    • Submission checklist drafted
    • Public GitHub repo created, licence visible in About
    • Register on Devpost — the page still shows a “Join hackathon” button, so this may be undone. It gates everything, including submitting.
    • Request the $150 AWS credits (form) — registered entrants only, closes 21 Oct, while supplies last. Covers roughly 75,000 graded cards, which is the whole project many times over.
    • Create the AWS account and enable Bedrock access — the live blocker on stage 1 and the critical path to stage 4.
    Exit: a judge could clone this and understand the intent without running anything.

  2. Spike the risky links

    Days 1–3 · 6 SepCurrent

    Prove the two things that could invalidate the plan, while pivoting is still cheap.

    • Confirm what Alexa+ Preview access a hackathon entrant actually gets — the MCP Toolkit is the documented path
    • Stand up a hello-world MCP server over Streamable HTTP — spike/hello_mcp.py
    • Connect from a real MCP client — fastmcp.Client and raw curl both handshake at protocol 2025-11-25; .mcp.json registers it for Claude Code
    • Confirm Bedrock model availability and region — us.anthropic.claude-sonnet-5, geo profile mandatory
    • Make one live Bedrock call — blocked: no AWS credentials on this machine (spike/check_bedrock.py is written and waiting)
    • Log every surprise in docs/FRICTION-LOG.md — four entries, two of them major
    Exit: a real MCP client gets a real response from a locally hosted server, and one Bedrock call has returned. Half met. The MCP half is proven end to end; the Bedrock half waits on credentials. The spike also cost the plan a new decision — Alexa+ enforces a sub-500 ms tool round trip, so grading had to be split into two calls (D7).

  3. Scheduler, test-first

    Days 4–8Pending

    SM-2 as pure functions. Correctness matters most here and is cheapest to verify here, which is why it leads.

    • Tests for the 0–5 quality bands, written before the implementation
    • Ease-factor floor and the reset-on-failure path
    • Multi-month interval growth verified with an injected clock
    • review() implemented, all tests green
    Exit: pytest passes with the algorithm exhaustively covered and no database in sight.

  4. Store

    Days 9–13Pending

    SQLite, one file, cards plus an append-only review log.

    • Schema for cards and reviews
    • Repository layer with integration tests against a temp database
    • Due-card query ordered by oldest debt first
    • Seeded demo deck for reproducible video runs
    Exit: cards survive a restart, and the review log can reconstruct a streak.

  5. Grader on Bedrock

    Days 14–22Highest value

    The differentiator. Server-side semantic scoring of a spoken answer, plus the calibration evidence that it is fair.

    • Scoring prompt returning a 0–5 quality and one spoken sentence
    • Calibration fixture set: answer pairs with expected score bands
    • Degrade safely when Bedrock is slow or unavailable — leave the schedule untouched
    • Empty or unintelligible transcript treated as “no answer”, never as wrong
    • Document the AWS integration in docs/PRODUCT-FEEDBACK.md
    Exit: the calibration suite passes, and the AWS Builder mini challenge is earned in code rather than claimed.

  6. MCP server and speech shaping

    Days 23–30Pending

    Four tools wired to the domain modules, with every response written to be heard rather than read.

    • list_due_cards, grade_response, add_card, get_streak_summary
    • Response length caps; no markup; no enumerations beyond three items
    • Tool descriptions legible to a model, not just to a human
    • End-to-end run driven from a real MCP client
    Exit: a full review cycle completes conversationally, start to finish, through MCP.

  7. Browser voice harness

    Days 31–36Pending

    Speech in and out via the Web Speech API against the same server. Insurance, usability test, and demo footage in one.

    • sim/ harness speaking to the MCP server
    • Listen to real responses and cut the verbosity you can only hear
    • Labelled clearly as a simulation, per the rules
    Exit: a full review done entirely by voice, screen ignored.

  8. Harden and open-source PR

    Days 37–41Pending

    Make the repo runnable by a stranger in five minutes, and earn the second mini challenge.

    • README verified by following it from a clean clone
    • One PR to a public repository, URL recorded
    • Licence confirmed visible in the GitHub About section
    Exit: judges who cannot run a project fall back on the video alone — this stage removes that risk.

  9. Demo video

    Days 42–45Pending

    Under three minutes, strongest thirty seconds first.

    • Open on the payoff: answer aloud, slightly wrong, graded on nuance, rescheduled
    • Architecture explained second, briefly
    • No third-party trademarks or licensed music
    • Public on YouTube or Vimeo, in English
    Exit: the first thirty seconds alone would earn a shortlist.

  10. Write-up and submit

    Days 46–49Pending

    The part most entrants rush. In a competition judged on the build plus the feedback, this is half the score.

    • Product feedback completed for every tool, SDK and AWS service used
    • Friction log tidied — severity, workaround, actionable suggestion on each entry
    • Tracks and mini challenges declared with their extra required fields
    • Submitted with days to spare, not hours
    Exit: submitted before 21 October. Never submit on deadline day.
Keep this file honest. Mark a task class="ok" only when it is genuinely done, and move the active class as stages close.
